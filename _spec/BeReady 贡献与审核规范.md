# BeReady 贡献与审核规范

BeReady 采用“先抛砖，再引玉”的建设方式：维护者先建立能力地图和初始节点，社区指出错误、补充经验和提供证据，AI 帮助整理为可审核的修改，最终由人工决定是否进入正式知识库。

初始节点可以不完整，但不能用未经确认的内容填满空白。允许留下边界清楚的缺口，不允许把猜测写成事实。

## 贡献入口

优先邀请用户：

- 指出错误；
- 补充适用条件和地区差异；
- 提供实践经验；
- 提供资料或验证线索；
- 提出缺失问题。

贡献者不需要先会写 Markdown。自然语言反馈可以由 AI 整理，但原始意见和 AI 整理结果必须区分。

## 贡献类型

### 纠错

修正事实、步骤、链接或安全问题。明显安全错误优先处理。

### 补充

增加遗漏条件、替代方法、环境差异、失败信号或操作细节。补充不得越过当前节点边界。

### 证据与经验

个人经验应保留地区、环境、材料、工具、操作过程、结果和已知失败条件。一次经验不能直接写成普遍规律。

资料应说明支持什么结论、适用于什么条件。正文不必堆砌机构名称，但审核过程要能追溯依据。

### 结构提案

新增、拆分、合并、移动节点，以及调整 Capability、Level、`_nav`、`_book`，都属于结构提案。先说明问题、影响范围、方案和理由，确认后再修改。

## AI 的职责

AI 可以：

- 搜索受影响节点；
- 归纳和去重反馈；
- 标出事实冲突与待验证内容；
- 建议节点边界和内部链接；
- 生成供人工审核的 diff；
- 检查 Markdown、front matter、链接和重复。

AI 不可以：

- 把社区意见自动认定为事实；
- 为了完整补写未经验证的数字、剂量、参数或经验；
- 因一次反馈批量创建节点或改变知识树；
- 自动合并高风险内容；
- 代替维护者决定最终知识。

## 审核等级

- 文字、格式、明确链接错误：一名维护者审核。
- 操作方法、节点边界、结构调整：熟悉相关规范的维护者审核。
- 医疗、药物、饮用水、食品、火、电、化学品和极端环境：需要可靠依据，并由具备相关知识的维护者审核。当前不强制双人复核；没有合适审核者时保持待验证或保留 PR。

暂时没有足够审核能力时，保持待验证或保留 PR，不为追求进度降低标准。

## `_PLAN.md` 的关系

`_PLAN.md` 记录候选缺口和工作优先级，不垄断社区反馈。

处理顺序通常是：

1. 明显安全错误；
2. 明显事实错误；
3. 已有节点缺失的关键步骤或条件；
4. `_PLAN.md` 中已确认的缺口；
5. 高质量社区补充；
6. 新领域和大型结构提案。

社区热点和传播数据不能直接决定知识架构。

## 合并与记录

每次正式合并至少说明：

- 改了什么；
- 为什么改；
- 影响哪些节点；
- 依据或经验是什么；
- 哪些内容仍未确认。

匿名提交只降低贡献门槛，不降低审核标准。无论通过网页还是 Git 提交，都必须形成可审阅的 diff，并经过人工 Review。

Git 保存知识的来源和演化过程。若使用 squash 合并，也应在 PR 中保留原始问题、关键依据和审核结论。

## 贡献者成长

贡献者可以自然经历：

> 读者 → 问题提出者 → 资料提供者 → 经验贡献者 → 节点贡献者 → 领域维护者

角色来自持续贡献和审核能力，不由一次提交自动获得。
