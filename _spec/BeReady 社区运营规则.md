# BeReady 社区运营规则

社区运营服务于核心纲领和知识改进，不以流量、用户数或内容数量作为最终目标。

基本循环是：

> 内容平台提出具体问题 → BeReady 承接已有知识与空白 → 社区挑错、补充经验和资料 → AI 整理影响范围 → 人工 Review → Git 留下演化过程 → 形成新的知识和问题

知识如何审核以 `_spec/BeReady 贡献与审核规范.md` 为准。本文只规定如何找到问题、邀请贡献和验证社区机制。

## 运营目标

分阶段验证：

1. **有人看**：具体问题能把读者带到对应知识节点。
2. **有人改**：读者愿意指出错误、补充条件或提供资料。
3. **有人持续维护**：贡献者逐步承担节点或领域的长期维护。

不在第一阶段追求大规模用户、群聊数量或全平台覆盖。

## 内容入口

对外传播具体问题，不把“知识库”本身作为主要选题。

优先选择：

- 普通人能够理解和讨论的问题；
- 已有基础节点、但仍有明确空白的问题；
- 能吸引实际经验或专业意见的问题；
- 可以落到一个节点或节点簇的问题。

每次采用“一题一文一节点簇”：

- 一篇内容只提出一个核心问题；
- 展示 BeReady 已经整理了什么；
- 明确哪些地方仍需挑错或补充；
- 链接到具体节点簇，而不是只链接首页；
- 不为了传播效果改变知识结论。

## 贡献邀请

优先使用低门槛、具体的邀请：

- 指出错误；
- 补充一个不适用的环境；
- 提供实际做法和结果；
- 提供资料或验证线索；
- 说明遗漏了什么问题。

避免只写“欢迎贡献”“欢迎加入社区”。贡献者不需要先会 Markdown，也不要求一次完成完整节点。

## 选题方向

第一阶段优先：

- 日常危机：停水、停电、断网、火灾、极端天气、食物变质、家庭急救；
- 判断落差：有水不等于能喝、会生火不等于会用火、有药不等于会用药；
- 传统和生活经验：储存、种植、制作、修理、节约和替代；
- 专业挑错：医疗、农业、户外、木工、电工、机械和通信。

不平均覆盖所有领域。先验证最容易产生真实反馈的主题。

## 渠道原则

维护一份核心内容，再按平台调整标题、长度和表达，不为每个平台生产互相冲突的知识版本。

搜索优化从具体问题出发，例如“雨水能不能喝”“停水怎么办”，让读者沿着：

> 具体问题 → 节点 → 相关节点 → `_book`

继续阅读。

Git 平台负责可信度、协作、审核和历史，不承担主要拉新任务。

## 第一阶段实验

先完成基础贡献条件：

- 首页能说明项目定位和未完成状态；
- `_nav`、`_book` 和节点之间可以正常进入；
- 有“指出错误 / 补充经验 / 提供资料”入口；
- 有贡献说明、Issue / PR 模板和审核规则；
- 维护者能够处理收到的反馈。

然后连续发布 10～15 个具体问题，每周 2～3 个。记录：

- 是否有人进入具体节点；
- 是否有人提出有效问题；
- 哪类邀请更容易获得反馈；
- 反馈能否经过 AI 整理和人工审核进入知识库；
- 维护者处理能力是否成为瓶颈。

跑通闭环后再扩大渠道，不用单次爆款判断项目成败。

## 主动邀请

有了一批真实问题后，再寻找相关经验者和专业人士。邀请应具体说明：

- 正在整理哪个问题；
- 目前哪里缺少经验或证据；
- 希望对方挑错、补充还是审核；
- 对方不需要承担完整写作。

不以泛泛的“加入开源项目”代替明确问题。

## 边界

- 传播热度不决定节点归属、Level、`_nav` 或 `_book`。
- 社区意见不自动成为事实。
- AI 生成的批量修改不自动合并。
- 没有维护和审核能力时，不扩大贡献入口。
- 不用灾难焦虑和猎奇内容吸引流量。
