# BeReady Wikilink 命名与链接规范

> 本文是《BeReady 文件组织与知识节点管理规范 2》的补充，只解决一件事：
>
> **`[[...]]` 里面到底应该写什么。**
>
> 本文不改变 Canonical Tree 的任何结构规则。

---

# 1. 解析规则

一个 `[[目标]]` 按下面的顺序解析，命中即停止：

```text
[[目标]]
   │
   ├─ 1. title             节点 front matter 的 title（必须全库唯一）
   │
   ├─ 2. filename          文件名，不含扩展名
   │
   └─ 3. 父目录/filename    仍然重名时，补一级父目录
```

| 优先级 | 匹配对象 | 说明 |
|---|---|---|
| 1 | `title` | 节点 front matter 中的 `title`。**全库必须唯一**，这是首选写法。 |
| 2 | `filename` | 文件名的 slug 部分，不含 `.md`。仅在 title 不适用时使用。 |
| 3 | `父目录/slug` | 当 slug 本身重名时（例如多个 `index.md`），补一级父目录消歧。 |

---

# 2. 为什么以 title 为第一优先

因为 Wikilink 指向的是**逻辑知识节点**，而不是物理路径。

规范已经确定：

> `filtration.md` 与 `filtration/index.md` 属于同一个逻辑节点。

所以链接不能绑定在文件名上。`title` 是节点的稳定身份，文件名和目录可以随重构变化。

---

# 3. title 的唯一性

`title` 是全局命名空间，**不能重复**。

出现同名时，不要用加后缀（`煮沸 2`）解决，而应该：

* 要么让两个节点各自表达更准确的概念；
* 要么确认它们其实是同一个节点，应当合并。

---

# 4. 写法约定

**默认写法：**

```markdown
[[煮沸]]
[[安全储水]]
```

**需要改变显示文字时，使用别名：**

```markdown
[[过滤|把水滤清]]
```

别名只改变显示，不改变解析结果。

**要点：**

* 默认写 `title`，不要写 slug。
* 不要写路径。`[[capabilities/water/L1/boiling.md]]` 是错的。
* 不要依赖大小写或空格差异来区分节点。

---

# 5. 什么时候允许写 slug

只有当目标节点**还没有 title** 时（例如尚未创建），才使用 slug 作为占位写法。

一旦节点建立，应把引用统一回 title。

---

# 6. 预告链接不是死链

Capability 的 `index.md` 中会出现大量指向**尚未创建节点**的链接：

```markdown
* [[自然水源]]
* [[地下水]]
* [[重力供水]]
```

这些是**待完善节点池**，属于能力路线图的一部分，不是错误。

因此：

> **不要把预告链接当成死链批量修复或删除。**

判断标准：

* 目标节点不存在，但语义上属于该 Capability 的未来方向 → **预告链接**，保留。
* 目标节点不存在，且写错了名字或根本不属于任何能力方向 → **死链**，需要修。

---

# 7. 死链的修复方式

修死链只做一件事：**把目标名改成正确节点的 title。**

```text
[[fire]]     → [[火]]
[[污染判断]]  → [[水源风险]]
```

不要借修死链的机会顺带改写正文。

---

# 8. 与结构规范的关系

本规范服从于《BeReady 文件组织与知识节点管理规范》：

```text
目录树     →  表达主要归属
Wikilink   →  表达语义关系
```

引用的 Level 与归属的 Level 无关，L1 可以引用 L3 的节点。

---

# 9. 校验清单

新增或修改节点后，检查：

```text
1. front matter 是否有 title
2. title 是否全库唯一
3. 正文中的链接是否都使用 title
4. 是否引入了新的、不属于任何能力方向的死链
5. 是否误改了预告链接
```
